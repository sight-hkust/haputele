# Explore HapuTele

This is the application's real UI, not a replacement prototype. All patient names, clinical values, signatures, accounts and tokens are synthetic. Every preview uses isolated API handlers; a production `NEXT_PUBLIC_API_URL` is ignored.

## Start with a user journey

Open **Journeys → End to end**. Play functions use the actual forms, hooks and route navigation. Replaying a story resets its synthetic server records and query/session state.

| Journey | Starting point | Observable result |
| --- | --- | --- |
| Initialize Clinic | Fresh setup | Token verification, institute/operator configuration, optional team setup, system workspace |
| Sign In And Search Patients | Anonymous login | Healthworker workspace, patient search, opened patient record |
| Register Patient With Consent | Consent gate | Drawn canvas stroke, demographic submission, new patient record |
| Book Pending Queue Entry | Queue deep link | Scheduled appointment; booked entry removed from pending queue |
| Write Sign And Queue Follow Up | Doctor's ready appointment | Draft notes persisted, prescription reviewed, six-week follow-up, completed locked appointment |
| Invite Doctor And Return To Roster | Admin invite form | New open invite appears in roster; no email is actually sent |
| Approve Doctor Application | Pending application | Active doctor; approval action disappears and deactivation becomes available |
| Update Institute Identity | System settings | Synthetic configuration saved and dirty state cleared |

## Inspect a feature or state

- **Screens / Public:** setup, login, doctor onboarding/rotation/expiry, phone capture/expiry and not-found.
- **Screens / Healthworker:** booking workspace and its deep links, patient roster/registration/record/intake, queue, availability, exports, and all seven appointment states.
- **Screens / Doctor:** own calendar, readiness, live/call boundary, draft/locked consultations, availability and practice profile.
- **Screens / Administration:** doctor approval/setup/rejection, invite/manual creation, healthworker roster, mixed operator roster and system configuration.
- **Clinical:** focused patient/intake/vitals/photos, booking/calendar, queue, consultation editors/review/follow-up/signing, slot selection and week painting.
- **Primitives:** controls, calendar keyboard/boundary states, status/error/loading/empty treatments, modals, camera/QR and signatures.
- **Shell:** role/session chrome, version footer and login graphic.

Use Docs for prop contracts and limitations, Controls for supported inputs, and the accessibility panel to inspect existing UI issues. Interaction stories run their play sequence in the canvas. Full-screen route stories intentionally omit autogenerated component docs to avoid multiple route mocks fighting over global Next navigation.

## Reset and dates

Reload or select another story before replaying a mutation journey. Synthetic API data lives only in that story's browser memory. Dates are relative to the current clinic day; calendars, elapsed slot restrictions and past-day painting use the real clock. Booking deep links and links between screens remain inside the same scenario. Primitive component links use Storybook's normal router action mocks.

## Boundaries, not fake integration proof

- **Video:** no usable LiveKit token is issued. Start/join requests return the real `livekit_not_configured` error. In-progress/awaiting-notes/completed fixture stories show the UI at those states, not an actual call.
- **Email:** invitation records are simulated. Resend delivery, suppression and webhooks need the real API and provider.
- **Consent/signature:** registration journeys draw actual canvas pixels for demonstration; saved signatures are labelled illustrations. Neither is legal consent or a clinical signature.
- **Camera/phone:** permission/device failures are safely demonstrated; camera success needs hardware/permissions and QR transfer needs the real backend plus a reachable phone. Preview tokens are inert.
- **Downloads:** export controls download valid labelled synthetic PDF/XLSX/ZIP files. Real prescription generation, manifests, date filtering and server security need integration verification.
- **Authorization/transactions:** MSW models UI responses, not PostgreSQL constraints, cookie/CSRF security, ownership, row locks or atomic operations.

No patient portal, reminder scheduler, backup/log/observability console or placeholder feature is presented as implemented. The walkthrough explains server-only integrations and code-only building blocks separately.
